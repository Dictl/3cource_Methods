# Проверка заявленных функций и артефактов

Статическая сверка. Для документа ниже указаны разделы и номера рисунков/таблиц; `location` указывает строки проверяемого кода (бинарный DOCX не имеет стабильных физических номеров строк).

1. **Нормы по операциям подменены расчётом по спецификации**
   - severity: `Error`
   - type: `Design`
   - location: `schema.sql:2079-2088`
   - description: PDF в разделе «Процедуры поддержки бизнес-логики» прямо требует `MR_Q` и `SUM_MR`, а в DOCX §4.1 и таблицах 4, 8 они заявлены как реализованные; в SQL и API их нет, и `calc_cost` считает материальную часть через `calc_bom`. Веб-блок материалов вызывает BOM напрямую (`core/static/js/route.js:478-487`), поэтому редактирование норм `route_operation_material` не меняет ни сводный расход, ни стоимость.
   - Наблюдаемый пример в начальных данных: `ПК-01.001` и `ПК-01.003` имеют материалы операций (`schema.sql:1924-1929`), но не имеют собственных строк BOM (начальные `INSERT` в `schema.sql:1150-1175`); для этих изделий материал в калькуляции равен нулю, хотя нормы в маршруте заданы. Это следствие того же дефекта, не отдельное замечание.

2. **Отчёт описывает поля и формулу из отсутствующей версии**
   - severity: `Warning`
   - type: `Documentation`
   - location: `schema.sql:1704-1735`
   - description: В DOCX §§1.2, 1.3, 2, 3, 4.1, таблицах 2–5 и заключении заявлены `setup_time`, `piece_time`, `result_state`, `source_operation_id` и формула `Tпз + Tшт·Q`; фактически таблицы хранят единственное `time_norm` на единицу, состояние и ссылка на операцию-источник отсутствуют, а SQL умножает норму на количество линейно (`schema.sql:2042-2048`, `2070-2073`). В ключевом списке PDF отдельный учёт Тпз не выделен, но в диаграммах проекта и тексте варианта 2 он есть: убрать из описания фактической реализации, а не утверждать, что его нет в PDF.

3. **Отчёт выдаёт анализ пропусков маршрутов за реализованную функцию**
   - severity: `Warning`
   - type: `Documentation`
   - location: `core/urls_api.py:127-132`
   - description: В DOCX §§1.3 и 4.1, рисунке 11 и таблицах 4, 8 заявлены `find_no_route` и `GET /api/technology/<product_id>/no-route/`, но их нет: SQL выдаёт только существующие операции через `JOIN latest` и `JOIN route_operation` (`schema.sql:2049-2052`), поэтому пропуск не виден. Это предложенная диагностика: например, если для самодельного фарша из состава батона убрать маршрут, нужен отдельный список таких позиций; покупные оболочка и клипсы не должны туда попасть. PDF требует обход существующих операций на всю глубину, не отдельный поиск пропусков (в таблице 4 DOCX соответствие процедуре задания — «—»).

4. **Пример анализа маршрута и параметры API не соответствуют контракту**
   - severity: `Warning`
   - type: `Documentation`
   - location: `schema.sql:1988-2025`
   - description: В §4.1 DOCX запрос `find_route_deep(id, 1000)` не выполнится с имеющейся одноаргументной сигнатурой; по таблицам 4 и 8 выбор `route_no` и `quantity` допустим, но API вызывает сервис только с `product_id` (`core/api_views.py:2045-2052`). SQL всегда выбирает максимальный номер для каждого изделия и показывает нормы на одно корневое изделие; это не нарушение одноаргументного `FIND_TM` из PDF само по себе.

5. **Калькуляция маскирует неполный маршрут как нулевую трудоёмкость**
   - severity: `Warning`
   - type: `Bug`
   - location: `schema.sql:2086-2088`
   - description: Если у изделия или собственного полуфабриката нет маршрута с операциями, внутренние соединения `find_route_deep` исключают его из `calc_labor` (`schema.sql:2049-2052`, `2070-2074`), а `calc_cost` всё равно возвращает сумму, подставляя 0 вместо отсутствующей суммы; пользователь видит правдоподобное число без признака неполноты. В том числе для маршрута без операций, который UI способен оставить после неудачного второго запроса (`core/static/js/route.js:316-350`). Диагностика неполноты калькуляции отличается от незаявленного обязательным отдельного поиска компонентов без маршрута.

6. **Патчи версии 8 и инкрементальное обновление схемы отсутствуют**
   - severity: `Warning`
   - type: `Documentation`
   - location: `core/bootstrap.py:43-65`
   - description: DOCX §§3–4 обещают `schema_patch_v8.sql` и автоматическое применение последовательности патчей при запуске. Код лишь принимает версии 5/6 (`core/bootstrap.py:12-14`), для прочих выдаёт ошибку, а чистая схема помечается версией 6 (`schema.sql:2091-2096`). В составе проекта файлов таких патчей нет.

7. **Заявленные проверки и результаты оставлены заглушками**
   - severity: `Warning`
   - type: `Documentation`
   - location: `core/tests.py:1-3`
   - description: DOCX §§4.1 и 5, заключение и приложение А ссылаются на тесты Django, Postman и прогон Newman. В `core/tests.py` только стандартная заготовка, `postman/route_api_tests.json` отсутствует, а в DOCX рисунки 5–17 и листинг содержат текстовые места под вставку (в архиве четыре фактически вложенных изображения для рисунков 1–4). Не следует выдавать эти иллюстрации за результаты запуска.

8. **Клиенту показываются кнопки изменения маршрутных данных**
   - severity: `WeakWarning`
   - type: `Documentation`
   - location: `templates/home.html:132-152`
   - description: В §5 заявлено, что элементы изменения доступны только администратору, но шаблон без условия `is_staff` выводит для клиента форму добавления и кнопки изменений; карточки операций также формируются без такой проверки (`core/static/js/route.js:177-197`). Серверный запрет записи остаётся (`core/middleware.py:36-46`), это несоответствие интерфейса описанию, а не обход прав.

9. **Маршрут не хранит граф состояний, описанный проектной моделью PDF**
   - severity: `Warning`
   - type: `Design`
   - location: `schema.sql:1726-1735`
   - description: У входного ресурса имеется ссылка только на изделие каталога, а не на результат операции; вложенность в `FIND_TM` получается из отдельной BOM (`schema.sql:2010-2019`). Это покрывает глубинный обход имеющихся маршрутов по составу, но не воспроизводит модель PDF «Изделие-Операция → входной ресурс → Изделие-Операция» и не поддерживает утверждение DOCX о потреблении промежуточного состояния внутри маршрута. В заключении стоит прямо назвать это упрощением.
