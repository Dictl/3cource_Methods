# Валидация соответствия предметной области и заданию № 6

Входные материалы найдены: `Задание №6.pdf` и `Отчёт_6_ИСПРАВЛЕННЫЙ.cleaned.docx`. PDF проверен через `pdftotext`, DOCX — через `word/document.xml`. Код и цепочки вызовов проверены по фактическим файлам. Классификация выполнена последовательно, по одному finding за раз.

## 1. Свод материалов берётся из спецификации вместо операций маршрута

**Вердикт: TP. Независимая severity: Error.**

`core/static/js/route.js:478–487` загружает `/api/bom/<id>/calc/`. Цепочка `core/api_views.py:1487–1493` → `core/service.py:1346–1358` → `schema.sql:1036–1077` вызывает `calc_bom`, который обходит `find_bom` (стр. 1067), а не `route_operation_material`. Таблица норм материалов операций действительно существует (`schema.sql:1727–1735`), и API её изменения есть (`core/service.py:2080–2121`), но guards там лишь валидируют значения и не подключают их к расчёту. Следовательно, MR_Q/SUM_MR из ключевых процедур PDF (стр. 21) не реализованы, а изменение нормы материала операции не меняет экранный свод. Последствие — обязательный расчёт материальных норм по маршруту выдаёт другой источник данных; вероятность проявления высокая при расхождении BOM и технологической нормы.

## 2. Стоимость материалов считается не по данным техпроцесса

**Вердикт: TP. Независимая severity: Error.**

`schema.sql:2079–2088` определяет `calc_cost`: material cost вычисляется как `SUM(c.total_cost)` из `calc_bom(p_id_prod, p_q)`, тогда как труд берётся из `calc_labor`. Цепочка API подтверждается `core/api_views.py:2063–2069` → `core/service.py:2141–2145` → SQL; UI вызывает её в `core/static/js/route.js:499–507`. Никакой защитной проверки или альтернативного чтения `route_operation_material` нет. Поэтому материал, назначенный только операции, не попадёт в себестоимость, а при несовпадении BOM и маршрута будет посчитан BOM; это непосредственно нарушает ключевое требование PDF о стоимости материальных ресурсов по техпроцессу (стр. 3). Вероятность высокая для любого такого расхождения.

## 3. Отчёт приписывает анализу технологичности поиск отсутствующих маршрутов

**Вердикт: TP. Независимая severity: Warning.**

В DOCX (абзацы 40, 168–172, 279–281, 370–372) заявлены `find_no_route` и `/technology/<id>/no-route/`. Поиск по проекту не находит ни функции, ни маршрута API. Реальная `find_route_deep` (`schema.sql:2011–2057`) формирует `items` из корня и `find_bom`, затем использует `JOIN route` (`:2049–2052`), поэтому компоненты без маршрута просто исчезают из результата; UI (`core/static/js/route.js:460–476`) показывает лишь сообщение об отсутствии строк. Guard `check_route_product` (`schema.sql:1942–1958`) запрещает маршрут для непроизводимых типов, но не реализует диагностику производимых компонентов без маршрута. Это расхождение отчёта с кодом подтверждено; оно относится к заявленной дополнительной функции, не к отдельной ключевой процедуре PDF. Вероятность вводящего в заблуждение описания высокая.

## 4. Пример вызова FIND_TM и выбор версии в DOCX не работают

**Вердикт: TP. Независимая severity: Warning.**

В DOCX абзацы 146–150 показывают `find_route_deep(id, 1000)`, а абзацы 276–278 и 368–369 заявляют параметры партии и `route_no`. Фактическая функция принимает только `p_id_prod` (`schema.sql:1989`), сервис вызывает только один параметр (`core/service.py:2130–2133`), API также принимает только `product_id` (`core/api_views.py:2045–2050`). В SQL CTE `latest` всегда выбирает максимальный `route_no` (`schema.sql:2021–2024`), а количество корня фиксировано как `1` (`:2011`). Это не пробел core-требования PDF: на странице 3 и в процедуре FIND_TM на странице 21 требуется `FIND_TM(pIdEl)` без этих параметров. Следовательно, finding подтверждён только как ошибка/расхождение DOCX, а не как нарушение базового FIND_TM; вероятность проявления при использовании описанного API высокая.

## 5. Отчёт описывает подготовительное время, которого нет в реализации

**Вердикт: TP. Независимая severity: Warning.**

В DOCX заявлены Tпз и формула в разделах 1.2–1.3, 2–4, таблицах 2–5 и заключении; абзац 146 также описывает `Tпз + Tшт · Q`. Фактическая схема содержит только `time_norm` на единицу (`schema.sql:1702–1714`). `find_route_deep` вычисляет часы как `unit_convert(ro.time_norm, ...) * i.qty` (`schema.sql:2042–2048`), а `calc_labor` лишь дополнительно умножает сумму на размер партии (`schema.sql:2062–2075`). Полей `setup_time`/Tпз и guards, компенсирующих их отсутствие, нет. PDF упоминает Tпз в иллюстративных моделях (стр. 8–9, 11–12), но это не сформулировано отдельной ключевой строкой на странице 3; поэтому это подтверждённое расхождение отчёта с кодом, но не самостоятельное нарушение ключевого core-требования. Вероятность ошибки расчёта высока, если Tпз требуется предметной моделью.

## 6. Граф состояний и входов операций заявлен, но не хранится

**Вердикт: TP. Независимая severity: Warning.**

DOCX (абзацы 74, 103, 199, 225, 237, 251, 255) заявляет `result_state` и `source_operation_id`; PDF на стр. 9, 11–13 в варианте 2 описывает состояния и связь потребителя с выходом конкретной операции. В фактической модели `route_operation` хранит только маршрут, порядок, справочники и `time_norm` (`schema.sql:1704–1715`), а `route_operation_material` ссылается непосредственно на `product_id` (`schema.sql:1727–1734`). `find_route_deep` строит исполнение по BOM (`schema.sql:2018–2019`) и соединяет операции маршрута (`:2049–2052`), не по входам/выходам операций. Guards и дополнительные таблицы состояния не найдены. Следовательно, конкретного источника входного изделия от предыдущей операции определить нельзя. Это подтверждённый пробел иллюстративной/расширенной модели PDF, не отдельная ключевая строка страницы 3; вероятность существенна для сценариев, где один продукт имеет несколько технологических состояний.

## 7. Типовые техпроцессы из проектного расширения не поддержаны

**Вердикт: TP. Независимая severity: Info.**

PDF на стр. 14–16 иллюстрирует общий шаблон, параметры конкретного изделия и расчёт по ним; DOCX описывает это расширение. В коде `route` привязан к конкретному `product_id` (`schema.sql:1692–1700`), операции принадлежат конкретному `route_id` (`schema.sql:1704–1707`), а `create_route` создаёт маршрут конкретного изделия (`core/service.py:1794–1817`). Поиск `template`, `flyweight` и параметризованных шаблонов в коде ничего не дал; guards только ограничивают тип изделия, но не создают шаблонную модель. Это подтверждённое отсутствие проектного расширения, а не нарушение ключевых требований PDF со страницы 3, поэтому severity ниже.

## Итог и неопределённости

Все семь записей из review-файла подтверждены как TP после проверки фактических цепочек вызовов и mitigating guards. Для первых трёх findings нарушение относится к ключевым требованиям PDF; findings 4–7 отдельно отмечены как расхождения отчёта или иллюстративной/расширенной модели, чтобы не выдавать модели PDF за core-требования. Неопределённых пунктов нет: оба входных файла присутствуют.
