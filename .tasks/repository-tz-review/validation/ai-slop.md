# Валидация `.tasks/repository-tz-review/review/ai-slop.md`

Входные файлы присутствуют: `Задание №6.pdf` и `Отчёт_6_ИСПРАВЛЕННЫЙ.cleaned.docx`. PDF проверен текстом `pdftotext`; DOCX — содержимым `word/document.xml`. Код и документы не изменялись. Находки проверены последовательно, по одной: для каждой прочитаны точные участки кода, прослежены вызывающие/вызываемые функции, проверены guards и альтернативные пути, затем независимо оценены последствие, вероятность, severity и вердикт.

## 1. Нормы операций не участвуют в расчёте материалов

**Вердикт: TP. Severity: Error. Вероятность: высокая. Точное место: `schema.sql:1726-1735`, `schema.sql:2079-2088`; вызовы: `core/service.py:2142-2146`, `core/api_views.py:2064-2068`, `core/static/js/route.js:478-487`.**

`route_operation_material` хранит нормы материалов для операций, но `calc_bom` (`schema.sql:1036-1077`) читает только `find_bom`. `calc_cost` получает материальную стоимость только из `calc_bom`; API вызывает именно `calc_cost`, а клиентский блок материалов обращается к `/api/bom/.../calc/`. Использования `route_operation_material` в расчётном пути нет, guard или альтернативного суммирования не найдено. В начальных данных нормы операций действительно создаются (`schema.sql:1910-1929`), в том числе для `ПК-01.001`/`ПК-01.003`, тогда как их собственные BOM-строки в показанных вставках отсутствуют. Поэтому изменение нормы операции не отражается в сводном расходе и стоимости.

PDF относит нормы расхода и сводные нормы к ключевым задачам (извлечённый текст, строки 27, 31-34) и прямо требует `MR_Q`/`SUM_MR` (строки 405-414). Это не смешивается с иллюстративной моделью состояний: здесь не реализована именно обязательная расчётная функция норм.

## 2. Отчёт описывает отсутствующие поля и другую формулу времени

**Вердикт: TP. Severity: Warning. Вероятность: высокая. Точное место: `schema.sql:1704-1715`, `schema.sql:2042-2048`, `schema.sql:2070-2074`.**

В `route_operation` есть единственное `time_norm`; полей `setup_time`, `piece_time`, `result_state` нет. В `route_operation_material` отсутствует `source_operation_id`. `find_route_deep` умножает `time_norm` на количество, а не вычисляет `Tпз + Tшт·Q`. Вызовы идут через `core/service.py:2131-2133` и `core/api_views.py:2045-2052`; совместимого слоя преобразования или guard нет.

DOCX утверждает эти поля, формулу и версию схемы в разделах 1.2, 1.3, 2, 3, 4.1 и таблицах 2-5. PDF действительно содержит Тпз/Тшт и модель состояний (текст PDF, строки 84-85, 110-114, 227-250), но это проектная/иллюстративная часть; она не доказывает наличие полей в фактической схеме. Следовательно, подтверждено искажение описания реализации, а не отсутствие требования из иллюстрации PDF.

## 3. `find_no_route` выдана за реализованную функцию

**Вердикт: TP. Severity: Warning. Вероятность: средняя/высокая при наличии компонента без маршрута. Точное место: `core/urls_api.py:130-132`, `schema.sql:2049-2052`.**

В URL зарегистрированы только `routes/`, `labor/` и `cost/`; поиска `find_no_route` и маршрута `no-route` в коде нет. `api_technology_routes` (`core/api_views.py:2045-2052`) вызывает только `find_route_deep(product_id)`. Внутри `find_route_deep` внутренние `JOIN latest` и `JOIN route_operation` исключают изделие/компонент без маршрута или операций, а не возвращают список пропусков. Guard или отдельная диагностика не найдены.

DOCX в разделе 4.1, рисунке 11 и примере SQL утверждает наличие `find_no_route` и результата проверки. PDF требует поиск строк техмаршрута на всю глубину (строки 29-30), а отдельная функция поиска пропусков не названа самостоятельной процедурой. Поэтому это TP несоответствия отчёта фактическому коду, но не отдельное нарушение обязательного API PDF.

## 4. Пример вызова `find_route_deep` в отчёте не соответствует сигнатуре

**Вердикт: TP. Severity: Warning. Вероятность: высокая для читателя, повторяющего пример. Точное место: `schema.sql:1988-2008`; трассировка: `core/service.py:2131-2133`, `core/api_views.py:2045-2050`.**

Функция объявлена как `find_route_deep(p_id_prod INTEGER)` с одним аргументом и выбирает последнюю версию маршрута через `DISTINCT ON ... ORDER BY ... route_no DESC` (`schema.sql:2021-2024`). Сервис и API также передают только `product_id`. В DOCX пример использует `find_route_deep(id, 1000)`, а описанная таблицами 4 и 8 версия также обещает дополнительные параметры; такой SQL с текущей сигнатурой завершится ошибкой. Это не следует считать нарушением PDF: PDF требует одноаргументный `FIND_TM(pIdEl)` (строки 405-409); ошибка относится к заявленному в DOCX примеру.

## 5. Неполный маршрут маскируется нулевой трудоёмкостью

**Вердикт: TP. Severity: Warning. Вероятность: средняя. Точное место: `schema.sql:2049-2052`, `schema.sql:2062-2075`, `schema.sql:2079-2088`; UI-путь: `core/static/js/route.js:316-350`.**

`find_route_deep` исключает позиции без найденного маршрута/операций внутренними соединениями. `calc_labor` суммирует оставшиеся строки, а `calc_cost` применяет `COALESCE(SUM(...), 0)` и возвращает стоимость без признака неполноты. API (`core/api_views.py:2064-2068`) не добавляет диагностику. Клиент сначала может создать пустой маршрут (`ensureRoute`, `route.js:316-323`), а операцию сохраняет отдельным последующим запросом (`:325-350`), поэтому пустое состояние достижимо. Guard полноты маршрута или предупреждение не найдено. Последствие — правдоподобная заниженная трудовая стоимость; вероятность зависит от наличия удалённого/пустого маршрута.

## 6. Заявленные патчи версии 8 и инкрементальное обновление отсутствуют

**Вердикт: TP. Severity: Warning. Вероятность: высокая при обновлении существующей БД. Точное место: `core/bootstrap.py:12-14`, `core/bootstrap.py:51-65`, `schema.sql:2091-2096`.**

Для новой схемы загружается только `schema.sql`, которое записывает версию 6. Файла `schema_patch_v8.sql` и прочих заявленных патчей в проекте нет. DOCX в разделах 3-4 обещает версию 8 и автоматическое применение `schema_patch_v2 … schema_patch_v8`. Это подтверждённое расхождение; инструкция о пересоздании БД не является инкрементальной миграцией.

## 7. Заявленные тесты, Postman/Newman и результаты не подтверждены артефактами

**Вердикт: TP. Severity: Warning. Вероятность: высокая для доверия к отчёту. Точное место: `core/tests.py:1-3`; отсутствует `postman/route_api_tests.json`.**

## 8. Не-администратору показываются элементы изменения маршрута

**Вердикт: TP. Severity: WeakWarning. Вероятность: высокая для обычного клиента. Точное место: `templates/home.html:132-152`, `core/static/js/route.js:177-200`.**

Шаблон выводит форму и кнопки создания/изменения маршрута без условия `is_staff`; карточки операций в JS также создают поля и кнопки сохранения, перемещения и удаления без проверки роли. ## 9. Схема не хранит граф состояний, описанный проектной моделью PDF

**Вердикт: TP. Severity: Warning. Вероятность: высокая для сценариев промежуточных состояний. Точное место: `schema.sql:1704-1715`, `schema.sql:1726-1735`, `schema.sql:1988-2008`.**

Схема хранит `time_norm`, а материал операции связывает только `route_operation_id` и `product_id`; ссылки на `result_state` или `source_operation_id` нет. `find_route_deep` строит вложенность через `find_bom`, а не через связи «операция-результат → входной ресурс». Это TP расхождения заявленной реализации с проектной моделью. При этом в ключевых требованиях PDF самостоятельный граф состояний не заменяет обязательные расчётные функции; поэтому находка не используется для подмены проверки `MR_Q`/`SUM_MR`.
