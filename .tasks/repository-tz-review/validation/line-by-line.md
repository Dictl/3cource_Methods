## Требования PDF отдельно от моделей и обещаний отчёта

- Раздел «Требования к системе» (строки 19–35 вывода `pdftotext -layout`) задаёт ведение изделий и операций с ресурсами, поиск строк маршрутов на всю глубину, сводные материальные и трудовые нормы и калькуляцию по техпроцессу. «Процедуры поддержки бизнес-логики» (строки 405–414) отдельно перечисляет `FIND_TM(pIdEl)`, `MR_Q(pIdTO, pQ)`, `SUM_MR(pIdEl, pQ)`, `TR_TO(pIdEl, pQ)`. Отсутствие эквивалентного расчёта важнее различия в именах функций.
- `Тпз`/`Тшт` показаны в аналитической и проектных моделях, а состояния и ресурсные связи — в проектном варианте 2 (строки 230–251). Это свидетельство предметной логики, но не требование к точным полям SQL/API. Отдельный endpoint для компонентов без маршрута, параметр партии у `FIND_TM` и именно Django-тесты не указаны в перечисленных основных требованиях и сигнатурах PDF; соответствующие замечания проверены по явным обещаниям DOCX.

## 1. Маршрутные операции хранят только одну норму времени

**TP · Warning** — `schema.sql:1702–1715`, `core/models.py:242–259`, `core/api_views.py:1899–1938`, `core/service.py:1958–2018`.

Отчёт (§3, таблица 5) заявляет замену `time_norm` на `setup_time` и `piece_time`. Маршруты создания и изменения (`core/urls_api.py:118–119`) передают из JSON только `time_norm` и `time_unit_id`; сервис проверяет ссылки и положительность нормы, присваивает её полю модели и сохраняет. SQL допускает единственный положительный `time_norm`, в комментарии он определён на единицу изделия. Проверки ссылок и размерности не добавляют второй нормы. Патча v8 в дереве нет; `core/bootstrap.py:12–14,43–69` описывает загрузку схемы и проверку совместимых версий, а не применение заявленного патча. `result_state` проверен отдельно в №6.

При попытке задать обе нормы ограничение неизбежно: хранится только одна. Операции с одной штучной нормой по-прежнему редактируются; численное последствие для партии проверено в №7.

## 2. Анализ технологичности не принимает размер партии

**TP · Warning** — `core/static/js/route.js:450–475,510–511`, `core/api_views.py:2045–2052`, `core/service.py:2130–2133`, `schema.sql:1989–2020,2042–2048`.

Отчёт (§4.1 и таблица 8) обещает анализ с размером партии. Поле с начальным значением 1000 (`templates/home.html:159–163`) вызывает пересчёт; JS читает число, но запрос `/routes/` отправляет без него. URL (`core/urls_api.py:130`) ведёт к обработчику, который не читает `quantity`; сервис проверяет существование изделия и вызывает SQL с одним аргументом. Корень получает `qty = 1`, компоненты — накопленный расход на одну единицу корня (не обязательно `1` для каждой строки); часы в ответе также рассчитаны на эту базу. В таблице UI показаны количество и норма времени, а не итоговые часы анализа. Отдельные запросы труда и себестоимости получают `quantity`, но не изменяют ответ `/routes/`.

Для партии больше единицы расхождение неизбежно. Поиск строк на всю глубину при этом работает, и PDF не требует партийного параметра у `FIND_TM`.

## 3. Нет расчёта норм материалов по операциям маршрута

**TP · Error** — `schema.sql:1035–1074,2078–2089`, `core/service.py:1345–1364,2080–2121`, `core/urls_api.py:127–132`.

PDF прямо требует расчёты для операции и для изделия; отчёт (§4.1, таблицы 4 и 8) заявляет `mr_q`, `sum_mr` и соответствующие API. Поиск по коду не обнаружил ни их, ни эквивалента: строки материалов операций можно хранить и менять, сервис проверяет нормы и единицы, но не рассчитывает партийный расход. `calc_cost` берёт материальную составляющую из `calc_bom`; та агрегирует `find_bom`, по умолчанию оставляя конечные позиции спецификации, а `route_operation_material` не читает. Приведение единиц и масштабирование BOM не устраняют различие источников.

Функция расчёта по маршруту отсутствует при любом вызове. Числа могут совпасть, если BOM совпадает с нормами процесса; при их расхождении закупочные количества и материальная часть себестоимости не отражают маршрут.

## 4. В блоке материалов маршрута показан расчёт BOM

**TP · Warning** — `core/static/js/route.js:478–487`, `templates/home.html:159–165`.

На вкладке маршрута блок «Материальные ресурсы» не маркирован как BOM. `loadRouteCalc` передаёт размер партии в `/api/bom/<id>/calc/`; URL (`core/urls_api.py:79`) ведёт к `api_bom_calc` (`core/api_views.py:1487–1495`), далее к `calc_bom` и `find_bom` (`core/service.py:1345–1358`, `schema.sql:1035–1074`). Обработчики ошибок и пустого результата не меняют источник; материалы операций для этой таблицы не читаются. Отчёт различает спецификацию и маршрутные нормы (§1.1, таблица 8).

Источник всегда BOM, ошибка интерпретации вероятна при отличающихся нормах. Сам расчёт спецификации корректен как отдельная функция; это UI-проявление №3, а не второй независимый сбой расчёта.

**TP · Warning** — `core/urls_api.py:130–132`, `core/api_views.py:2045–2052`, `core/service.py:2130–2133`, `schema.sql:2010–2025,2049–2052`.

## 6. Не хранятся состояния изделия и ссылки на операции-источники

**TP · Warning** — `schema.sql:1702–1715,1726–1735`, `core/models.py:242–259,274–286`, `core/api_views.py:1998–2029`, `core/service.py:2080–2121`.

Отчёт (§2–3) заявляет `result_state` для выхода и `source_operation_id` для потребления полуфабриката внутри маршрута. В DDL и ORM этих атрибутов нет; API записи операции их не принимает (`core/api_views.py:1899–1938`), а API и сервис материалов принимают изделие и норму, не идентификатор операции-источника. Проверка в `add_operation_material` запрещает ссылаться на изделие собственного маршрута; она не кодирует связь с результатом предыдущей операции. Название и порядок операций позволяют описать последовательность, отдельно заведённое изделие — подключить полуфабрикат, но ни один вариант не сохраняет явную внутримаршрутную зависимость.

Граф потребления нельзя выразить при любом вводе через штатный API. Последствие существенно для процессов с промежуточными результатами, но простые линейные маршруты доступны. PDF иллюстрирует концепцию «Изделие-Операция», а не имена полей отчёта.

## 7. Расчёт труда не учитывает подготовительное время партии

**TP · Error** — `schema.sql:2042–2048,2061–2076,2086–2088`, `core/api_views.py:2054–2068`, `core/service.py:2135–2146`.

Путь `/labor/`: обработчик читает `quantity`, сервис проверяет его и вызывает SQL `calc_labor`. Тот получает часы из `find_route_deep` как переведённую в часы норму `time_norm × количество компонента`, затем умножает итог по профессии на `p_q`. Стоимость труда рассчитывается аналогично с тарифом и округлением; `/cost/` использует тот же итог труда. Проверка количества, пересчёт единиц и округление не добавляют фиксированного слагаемого. Отчёт (§2, §4.1) обещает `Тпз + Тшт × Q`; PDF требует сводный трудовой расчёт, разделение норм показано в моделях.

При ненулевом `Тпз` модель систематически не учитывает фиксированную работу, от которой зависят часы, трудовая стоимость и цена единицы; при нулевом `Тпз` такого расхождения нет. №1 описывает отсутствие входных данных, №7 — наблюдаемое следствие для отчётных итогов.

## 8. Нет заявленного набора автоматических тестов Django

**TP · Warning** — `core/tests.py:1–3`, `manage.py:11–18`, `config/settings.py:37`.

DOCX §4.1 обещает сверку `find_route_deep`, `sum_mr`, `calc_labor`, `calc_cost` и проверку однократного учёта `Тпз` через `python manage.py test`. Там же показана отдельная SQL-проверка триггера; текст не называет её Django-тестом, поэтому эту часть исходной формулировки не подтверждаю. `core/tests.py` содержит только импорт `TestCase` и комментарий. Стандартной точке входа Django не сопутствует ни отдельная команда `test`, ни иной проектный тестовый модуль, `load_tests` или настройка `TEST_RUNNER`; SQL-примеры не заменяют обнаруживаемые тесты.

В текущем дереве запустить именно заявленные проверки невозможно; это недостаток проверяемости и защиты от регрессий, а не самостоятельный сбой приложения. PDF не устанавливает использование Django-тестов.
