## 1. Расчёт по спецификации подменяет нормы материалов техпроцесса

**TP · Error · Bug** — `core/static/js/route.js:478–487`, `schema.sql:2086–2088`.

- **Требование:** PDF, стр. 3 и 21, требует нормы по операциям и свод по изделию, а также стоимость по техпроцессу. DOCX (абз. 146, 157–167, 282–296) заявляет `mr_q`/`sum_mr` по маршрутам, получение стоимости материалов из `sum_mr` и прямо отличает эти функции от `calc_bom` по конструкторской спецификации.
- **Цепочка чтения:** таблица «Материальные ресурсы» вкладки маршрута (`templates/home.html:159–170`) наполняется ответом `/api/bom/<id>/calc/` (`core/static/js/route.js:478–487`) → `core/urls_api.py:79` → `core/api_views.py:1489–1495` → `core/service.py:1346–1358` → `calc_bom`, который берёт `find_bom`/`bom_effective` и цену изделия (`schema.sql:1057–1075`). Калькуляция по `/api/technology/<id>/cost/` (`core/static/js/route.js:500`, `core/urls_api.py:132`, `core/api_views.py:2065–2070`, `core/service.py:2142–2146`) также передаёт стоимость материалов из `calc_bom`, а не из операций (`schema.sql:2086–2088`).
- **Цепочка записи и ограничения:** `core/static/js/route.js:432–438` → `core/urls_api.py:128` → `core/api_views.py:2018–2029` → `core/service.py:2110–2121`: валидация нормы, базового количества и единицы, затем сохранение только строки `RouteOperationMaterial`. В схеме нет синхронизации этой таблицы со спецификацией; поиск по коду не обнаружил `mr_q`, `sum_mr` или альтернативного агрегирования по `route_operation_material`. Валидация изделия/количества и повторная загрузка деталей после сохранения не меняют источник расчёта. Совпадение исходных норм маршрута и состава может скрыть расхождение, но не гарантируется.
- **Вероятность и последствия:** при независимом изменении нормы в операции и неизменной спецификации результат систематически не отражает изменение: сводная потребность и материальная доля себестоимости могут быть неверны. Это отказ основной функции для штатного сценария редактирования, поэтому `Error`; отдельный свод по спецификации сам по себе корректен как иной результат.

## 2. Расчёт затрат труда переиспользует округлённую стоимость на единицу

**TP · Warning · Bug** — `schema.sql:2069–2074` (источник округления: `schema.sql:2046–2048`).

- **Требование:** PDF, стр. 3 и 21, требует расчёт трудовых ресурсов и стоимости труда по техпроцессу; точку округления не задаёт. DOCX (абз. 146, 152–156, 288–293) описывает масштабирование накопленного количества на партию, группировку по профессии/разряду и включение стоимости труда в себестоимость. Раннее округление не является частью описанного контракта.
- **Цепочка:** вкладка запрашивает `/api/technology/<id>/labor/` (`core/static/js/route.js:489–497`, `core/urls_api.py:131`) → `core/api_views.py:2056–2061` → `core/service.py:2136–2139` → SQL `calc_labor` (`schema.sql:2069–2074`). `find_route_deep` отдаёт часы без округления до копеек, но денежную величину `labor_cost` округляет до двух знаков на каждой строке до группировки и умножения на партию (`schema.sql:2046–2048`). Стоимость труда, общая стоимость и расчёт цены единицы наследуют эту погрешность через `calc_cost` (`schema.sql:2086–2088`).
- **Статическая сверка:** исходный состав содержит 440 г фарша на батон (`schema.sql:1131,1162`), норматив куттерования — 2 минуты на единицу фарша в кг, ставка — 380 руб./ч (`schema.sql:1828,1865`). Для вклада этой операции при текущей модели времени `0,44 × 2 / 60 × 380 = 5,57333…` руб. на батон. Округлив перед масштабированием, код получает 5 570,00 руб. на 1000 шт. вместо 5 573,33 руб. при округлении стоимости партии. Это сравнение порядка округления, а не полная калькуляция батона по формуле DOCX.
- **Ограничения, вероятность и последствия:** проверка положительности количества (`core/service.py:1184–1191`) не предотвращает потерю точности; финальное округление тоже не восстанавливает её. При стоимости операции, кратной копейке, этого источника погрешности нет, но пример относится к штатным исходным данным и партии из интерфейса. Ошибка по модулю до половины копейки на строку до масштабирования растёт с партией; вклады могут частично компенсироваться. Это денежная погрешность без отказа расчёта часов, поэтому `Warning`.

## 3. Ответы предыдущего выбора перезаписывают текущие расчёты в интерфейсе

**TP · Warning · Concurrency** — `core/static/js/route.js:450–511`.

- **Требование:** PDF, стр. 3 и 21, требует расчёты по изделию и количеству, но не определяет управление параллельными запросами. DOCX (абз. 40, 152–167) описывает интерфейс технолога и расчёты на конкретную партию. Замечание касается соответствия отображаемого результата выбранным параметрам, а не расхождения с иллюстративной моделью.
- **Цепочка вызовов:** изменение количества или отправка формы вызывают `loadRouteCalc` напрямую (`core/static/js/route.js:510–511`). Смена изделия меняет `routeState.productId` и запускает `loadRouteProduct` (`core/static/js/route.js:268–272`); та вызывает `loadRouteCalc` напрямую или после асинхронной загрузки деталей (`core/static/js/route.js:110–160`). `loadRouteCalc` захватывает изделие и количество, отдельно запрашивает маршрут, материалы, труд и калькуляцию (`core/static/js/route.js:450–507`). API использует переданный идентификатор и, где применимо, количество (`core/urls_api.py:79,130–132`, `core/api_views.py:1489–1495,2047–2070`); каждый обработчик ответа или ошибки пишет в общий блок без сверки с текущим выбором.
- **Проверка защиты:** отсутствие изделия останавливает только новый вызов, а не ранее запущенные запросы. `apiRequest` запускает `fetch` и ограничивает ожидание 15 секундами (`core/static/js/common.js:59–76`); этот тайм-аут не упорядочивает ответы и не отменяет прежний запрос при новом выборе. Ни проверок актуальности, ни отмены запроса в пути записи не обнаружено.
- **Вероятность и последствия:** при перекрытии запросов порядок завершения не гарантирован; запоздалый ответ может оставить стоимость, часы или нормы от предыдущего выбора рядом с актуальными данными до следующего обновления. Без перекрытия проблемы нет, частота зависит от задержек и действий пользователя. Это значимое искажение показаний интерфейса без изменения данных на сервере, поэтому `Warning`.

**Итог:** 3 TP, 0 FP, 0 NeedMoreData. Код и исходные документы не изменялись; сценарии не запускались.
